## 四、判卷预案（用户答 X 怎么接）

### Q0-2（背景核实）
- **答"是真的/在做"** → 把项目细节问清（数据量、代理模型精度、当前卡点），写进 `LEARNINGS.md`
  知识背景节，之后每次会话第 5 步"连接"都用真实项目；上游 `agent-opening.md` 的提问策略全部生效。
- **答"不是/没这项目"** → 立即作废上游那份 `agent-opening.md` 的用户画像，
  把"连接"环节改成连本仓库已学学科（概率论 PCA/协方差、数理方程 PDE、工程力学优化）；
  在 `ERRORS.md` 记一条判例："未核实上游技能里的用户画像就当真"。
- **答"部分是真的/以前想做"** → 按"假设式连接"处理，每次用"如果你要做 X"句式，不写进 MEMORY.md。

### Q2（瓶颈排序）
- **答"CFD 太慢"** → 对，但只答了一半。追问："慢是瓶颈，那第二个瓶颈是什么？"
  引到 p5 的原文："高计算成本 + 高维设计空间是**两个复合挑战**（two compounding challenges）"。
- **答"设计变量太多/维度高"** → 很好。追问："那为什么不用少一点的参数化？"引到 p5 NACA/PARSEC 自由度不足。
- **答"网格/收敛"** → 部分对（p6 挑战①提到畸形形状导致 CFD 不收敛）。肯定后再引到完整六条。
- **完全没猜到"多目标太贵/不确定性/多保真度/不连续/交互式"** → 这正是打脸点，
  在会话02 把六条完整列出，让他标 ✅/⚠️/❌/🆕。

### Q3（设计变量数量下注）
- 论文实物答案（p5）：**二维翼型需要"几十个"（tens）设计变量；三维机翼需要"几百个"（hundreds）**。
- 用户答 <10 或 >1000（二维） → 打脸，给原文并问"为什么这么多？少了会怎样"。
- 用户答几十/几百 → **明确说"你答对了"**（低自信型答对，见 LEARNINGS），再追问"为什么不能只用 5 个"。

### Q4（为什么还需要 ML）
- 论文实物答案（p3、p6–7）：伴随方法解决了"梯度贵"，但没解决"每次函数评估仍然贵"，
  于是满足不了**交互式设计的近实时要求**（挑战⑥），也扛不住**多目标**（②）与**不确定性**（③）。
- 用户答"因为 ML 更快" → 太笼统。追问："快在哪一步？替代了循环里的哪个框？"（引 Fig.1）
- 用户答"梯度法只能找局部最优，ML 能全局" → **这是个常见误解**，论文没这么说，
  不要顺着夸；指出 §4.3 讲的是架构改造而非全局寻优。
- 用户答不出 → 提示阶梯第 ③ 级："看 Fig.1 的工作流，哪一步最耗时？ML 能替代哪一步？"
