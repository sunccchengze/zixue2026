# 课题10 开题简报 · 长程 Agent 与 self-judge

> 模块：**M8** ｜ 周次：**W14（12-14→12-20）** ｜ 算力：**T2 Kaggle 2×T4，计划 8 GPU·小时**
> 唐杰作业对应：**⑤ 训长程 Agent，鼓励 self-judge loop** ｜ 判分来源：**自建**（消融实验 + 轨迹日志）
> 手写：**R10（self-judge 协议设计）**

## 一、研究背景

从"回答问题"到"完成任务"的跨越，靠的是 **harness（外壳）**：工具调用、上下文管理、失败重试、自我评估。
Karpathy 与李宏毅都专讲 **context engineering**；nanochat 里 `execution.py` 就是一个最小的"能执行代码的 Agent 外壳"。
本课题的落点是**长程任务**：多步串联后误差累积，以及**self-judge（自我评判）到底有没有用**。

## 二、研究问题

> **多步任务中，失败主要来自模型能力还是来自 harness 设计？加上 self-judge loop 后成功率提升多少——还是反而下降？**

## 三、攻关线索

1. **最小 ReAct**：不用任何框架，手写 `Thought → Action → Observation` 循环（三四十行就能跑）
2. **工具设计**：先给两个工具（计算器 / 受限代码执行）。**工具接口的清晰度往往比模型智力更决定成败**
3. **长程任务构造**：把课题09 的题改造成"需要 3–5 步"的复合任务（如：先算 → 再验 → 再格式化）
4. **失败分类**：格式错 / 工具调错 / 目标漂移（忘了原始要求）/ 循环打转 / 提前放弃
5. **self-judge 的两种形态**：
   - **自评重试**：模型给自己打分，低于阈值就重做（rasbt ch5 的 self-refinement）
   - **自评过滤**：生成多个候选，自己挑最好的（best-of-N 的变体）
6. **关键实验（消融）**：同样的任务集，三组对照 = 无 self-judge / 自评重试 / 自评过滤
7. **警惕**：self-judge **会放大原有错误**（模型判不出自己错在哪，反而确信）→ 必须留失败案例

## 四、里程碑

- [ ] M2 加入第二个工具 + 多步任务集（≥30 个任务）
- [ ] M3 **轨迹记录规范**：每步的 thought/action/observation 落盘（可复现）

## 七、代码级提问示例

1. 长程任务失败率随步数指数上升。**分解**：是每步错误率问题，还是错误会累积传播？
2. self-judge 什么时候**一定**无效？（提示：当模型无法区分"看起来对"和"真的对"时）
3. 上下文压缩（截断/摘要）会引入什么新失败模式？
4. 为什么"工具返回值要结构化"能显著提升成功率？（从 token 分布角度解释）
5. **【下注】** 预测 self-judge 在简单任务 vs 困难任务上的效果差异，先写再测。

## 八、风险与提醒

- 🚨 **不要用框架起步**：手写一遍 ReAct 再去看 LangGraph/smolagents，否则学不到 harness 的本质。
- ⚠️ self-judge 会显著增加 token 消耗与时间 → 算力预算要写进实验卡。
- ⚠️ 轨迹日志可能很大 → 只保留结构化摘要（thought 截断 + 结果），避免污染仓库体积。
