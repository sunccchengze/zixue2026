## 一、压缩视角：BPE 到底在做什么

**一句话**：给定词表预算 V，BPE 反复执行"找出当前出现次数最多的相邻 token 对 → 合并成一个新 token"。每合并一次，语料的总 token 数减少一点，直到词表填满 V。

形式化：把语料看成一串字节 $b_1 b_2 \dots b_n$。定义当前切分下相邻对 $(x,y)$ 的频次 $c(x,y)$。每步选
$$(x^*, y^*) = \arg\max_{(x,y)} c(x,y)$$
把语料中所有该对合并为新 token $xy$，并把 $(x,y)$ 记入 merges 列表（顺序即"资历"）。

**关键推论 A（压缩率）**：合并的收益可以直接量化——每合并一处，总 token 数减 1。所以"BPE 训练过程"就是"贪心压缩过程"，merges 列表本质是**一本压缩字典，且按收益从大到小排序**。

**关键推论 B（为什么 loss 不可跨分词器比较）**：token 越少 → 每个 token 承载信息越多 → 单 token 的交叉熵必然更高。这是记账单位问题，不是模型好坏。所以跨分词器比较必须换成**与切分无关**的单位：bits-per-byte（bpb）。

> **这条是新课标里最重要的一条**：nanochat 全程用 bpb 而不是 loss 来跨模型比较，课题03（scaling law）和课题08（RL 对照）都会回到这里。

## 二、为什么必须字节起步（以及代价）

从 **Unicode 字符**起步的三个具体麻烦：

| 麻烦 | 具体例子 | 后果 |
|---|---|---|
| 词表爆炸且长尾 | 仅 CJK 就有 9 万余字符，常用仅数千 | 大部分字符训练不充分，嵌入近乎随机 |
| 永远有未登录 | 新 emoji（每年新增）、生僻字、方言字 | 无兜底机制 → OOV，直接崩 |
| 失去字节级共享 | "妈"与"吗"共享部首但完全不同字符 | 学不到字形/字节层面的结构 |

从**字节**起步：任何文本 → UTF-8 → 0–255 的字节序列 → 这 256 个 token 永远在词表里。
**所以字节级 BPE 永远不存在"无法表示的输入"，只可能被切得更碎。** 这就是"零风险"的含义。

**代价（必须知道，因为它是第 1 题的答案关键）**：
- 汉字 UTF-8 占 **3 字节**；英文常用词常被合并成 1 token，而中文常需 1.5–2 个 token 表示 1 个汉字
  （取决于词表大小与语料配比）→ **中文的"每字成本"高于英文**
- 序列变长 → 注意力计算量（O(L²)）上升 → 中文推理成本更高

## 三、训练算法：从 O(n²) 到官方要求的 <1.5 秒

**朴素想法的三个陷阱**（都会导致超时或超内存）：

1. **每步重扫全语料**统计相邻对 → O(V · n)，V=500、n≈百万级就是灾难
2. **用字符串做合并**（`text.replace("ab","ab_new")`）→ 每次 O(n) 拷贝 + 无法区分"新合并的 token"与"原始字符"
3. **把语料整体读入内存再展开成 token 列表** → 5MB 语料 + 1MB 配额的内存测试必挂

**正确方向的三个要点**（方向，不是实现）：
- **词频级统计而非字符级**：同一种"词"（如 ` the`）在语料里重复百万次，只需统计一次它的结构，再按词频加权
- **增量更新**：一次合并只影响"包含该对的相邻位置"，其余的对频次不变 → 只需局部更新
- **优先队列/堆**：快速取出当前最高频的对，而不是每步全量排序

> 官方参考实现 0.38 秒，"玩具实现"约 3 秒——**这 8 倍差距就在上面三点里**。

## 四、编码：回放合并历史，而不是最长匹配

编码时我们**没有语料统计**，只有 merges 列表（一个有序的"合并历史"）。正确做法：

```
把文本按 UTF-8 切成字节数组
loop:
    找出当前序列中所有相邻对里，在 merges 中"排名最靠前"（资历最老）的那一对
    合并它
    直到没有任何相邻对出现在 merges 中
```

**为什么不是"最长匹配优先"？** 因为训练时每一次合并都遵循"最老优先"的规则；
若编码用另一套规则，同一个子串在不同上下文会被切成不同 token，
**与 tiktoken/GPT-2 的逐 id 对齐测试必然失败**。BPE 的编码本质是**回放训练时的决策序列**。

**特殊 token 是另一套优先级**：它们**不参与合并**，且在编码时**先于普通文本被匹配**。
注意两个官方测试点名的情况：**重叠**的特殊 token（如 `a` 与 `ab` 同时存在）与
**尾随换行**（`<|endoftext|>\n`）——这类边界的处理顺序会直接决定对错。

## 五、接口设计决定内存上界（`encode` vs `encode_iterable`）

官方测试里有一个耐人寻味的设置：

| 方法 | 官方态度 |
|---|---|
| `encode(text)` | 被 `xfail` 标记：*"encode 预期会超过 1MB 配额"* —— **超了也原谅** |
| `encode_iterable(iterable)` | 用 `RLIMIT_AS` 硬限 1MB，读 5MB 语料 —— **超了就失败** |

**为什么这不是双标**：接口的**输入形态**决定了它的内存下界。
`encode(str)` 的输入本身就是一整段字符串，它已经在内存里了——上界由输入决定，实现者无能为力。
`encode_iterable(iterable)` 的契约是**流式**：输入是迭代器，实现就必须逐块处理、边读边 yield。
任何 `list(iterable)` / `"".join(iterable)` / 先聚合再编码的写法，都违背了接口语义。

> 这是**软件工程里最漂亮的一课**：接口不只是名字，它是**约束**。
> 同一个算法，换个接口，内存上界就从"输入大小"降到"块大小"。这个思想在课题05（KV cache）、
> 课题07（数据流式清洗）、课题10（长程 Agent 的记忆压缩）都会反复出现。

## 六、词表大小的三方权衡（第 1、4 题的答案框架）

词表从 V 扩到 4V，同时影响三件事：

| 受影响项 | 方向 | 机理 |
|---|---|---|
| 嵌入/输出层参数量 | ↑ 约 4 倍 | 参数 ∝ V·d（若权重共享则 1 份，否则 2 份） |
| 同文本序列长度 L | ↓ | 更多常见片段被合并 → token 数下降 |
| 每 token 的注意力计算 | ↓ 约 L² 下降 | 注意力是 O(L²·d) |
| 罕见 token 的训练充分度 | ↓ | 长尾 token 出现次数少，嵌入学不好 |

净效果**不是单调的**：太小 → 序列太长、算力烧在长度上；太大 → 参数浪费 + 长尾欠训练。
经验上 32k–128k 是常见区间（GPT-2 用 50257，现代模型多在 100k 量级，且对多语言友好）。

**中文特例**：词表若中文覆盖不足，一个汉字可能被拆成 3 个字节 token，
**中文成本直接翻 2–3 倍**——这是国产模型普遍重视中文词表预算的原因。

## 七、常见误解（每条配反例）

| 误解 | 反例 |
|---|---|
| "一个 token 就是一个词" | `▁transformer` 可能是 1 个 token，`妈` 可能是 3 个 token（UTF-8 三字节） |
| "分词只是预处理，不影响模型能力" | 词表决定序列长度 → 决定有效上下文与算力分配 → 直接影响能学到什么 |
| "编码用最长匹配更聪明" | 会与训练决策不一致 → 与 tiktoken 逐 id 对齐测试直接失败 |
| "词表越大越好" | 长尾 token 训练不足 + 嵌入层参数浪费；存在经验最优 |
| "decode 一定无损" | 只有在**完整 utf-8 序列**上才无损；单 token 解码可能是半个字符（`�`） |

## 十、记忆锚

- **隐喻**：BPE = **"贪心的拼音缩写机"**——不停找最常一起出现的两段，把它们缩成一个新记号，
  缩到最后词表满了；字典按先来后到排资历。
- **口诀**：**"字节兜底、频次贪心、老手优先、流式省内存"**（对应：字节起步 / 训练目标 / 编码回放 / 接口约束）
- **符号位置法**：$V$（词表）在上，撑着两件事：下面是 **参数量 ∝ V·d**，右边是 **序列长度 L ↓**；
  三者写成一个三角形，随时能想起"扩词表 = 拿参数换长度"。
