### 卡号 M2-01 · 字节回退（byte fallback）为什么是零风险设计
- **问**：词表里那 256 个基础 token 是什么？为什么有了它们，就不存在"未登录字符"？
- **答（核心）**：任何文本 → UTF-8 编码 → 一律变成 0–255 的字节序列；256 个字节全部在词表里，
  所以任何输入都能被表达，只可能切得更碎，绝不可能"无法表示"。
- **代码定位**：`手写/bpe.py` 的 vocab 初始化（256 个单字节 + 特殊 token）
- **反例/边界**：emoji（4 字节）、生僻汉字（3 字节）、换行与控制字符（1 字节，不可见易漏）
- **首次建立**：2026-09-17 · 课题01 讲解（待用户复述确认）
- **复习记录**：⬜
- **leech 标记**：无

### 卡号 M2-02 · 压缩率 ↔ 词表大小的三方权衡
- **问**：词表从 32k 扩到 128k，同时影响了哪三样东西？方向分别是什么？
- **答（核心）**：①嵌入/输出层参数量 ↑（约 4 倍）②同文本序列长度 ↓（注意力计算 ↓）
  ③每 token 的统计效率 ↓（罕见 token 训练不充分）。总效果不是单调的，存在经验最优点。
- **代码定位**：`手写/bpe.py` 里 `vocab_size` 参数的语义（含特殊 token 的**总数**）
- **反例/边界**：中文：汉字 UTF-8 占 3 字节，词表不足时一个汉字会被切成 3 个 token → 中文成本翻倍
- **首次建立**：2026-09-17 · 课题01 讲解
- **复习记录**：⬜
- **leech 标记**：无

### 卡号 M2-03 · 为什么合并顺序不能改成"最长匹配优先"
- **问**：编码时若按"最长匹配优先"而不是"按 merge 的创建顺序"，会发生什么？
- **答（核心）**：会与训练时的合并历史不一致 → 同一个词在不同位置被切成不同 token，
  且**与 tiktoken/GPT-2 的 id 对不上**（官方测试逐 id 比对）。BPE 的编码是"回放训练时的合并序列"。
- **代码定位**：`Tokenizer.encode` 里的 `merges` 排名表（rank/priority 查表）
- **反例/边界**：`test_overlapping_special_tokens` 说明特殊 token 的匹配优先级又是另一套规则
- **首次建立**：2026-09-17 · 课题01 代码级提问 Q2
- **复习记录**：⬜
- **leech 标记**：无

### 卡号 M2-04 · 接口设计决定内存上界（`encode` vs `encode_iterable`）
- **问**：为什么同一个分词器，`encode()` 超 1MB 内存被官方**原谅（xfail）**，而
  `encode_iterable()` 超 1MB 就算**失败**？
- **答（核心）**：`encode(str)` 必须先把整段文本放进内存（输入本身就是完整字符串，上界由输入决定）；
  `encode_iterable(iterable)` 的契约是**流式**——输入是迭代器，实现就必须逐块处理、即时 yield，
  不允许 `list(iterable)` 或 `"".join(...)`。**接口的语义决定了内存上界，不是实现技巧。**
- **代码定位**：`手写/bpe.py` 的 `Tokenizer.encode_iterable`（必须是 generator）
- **反例/边界**：5MB 语料 + 1MB 配额下，任何"先聚合再编码"的写法都会 OOM 崩掉
- **首次建立**：2026-09-17 · 课题01 官方判分标准探明
- **复习记录**：⬜
- **leech 标记**：无
